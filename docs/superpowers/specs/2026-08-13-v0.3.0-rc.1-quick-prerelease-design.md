# v0.3.0-rc.1 Transparent Quick Prerelease Design

## Decision

Publish an unsigned, public GitHub **pre-release** with tag `v0.3.0-rc.1`.
The executable product version remains `0.3.0`; the distinct release tag leaves
the eventual stable `v0.3.0` tag and its immutable assets available for the
complete release process. The pre-release contains the same six candidate
assets required by the existing dual-platform pipeline: Windows x64 setup and
its checksum/provenance, plus macOS arm64 DMG and its checksum/provenance.

This is not a stable `v0.3.0` release. The public notes, embedded Windows
provenance, candidate summary, and validation evidence must all say that the
130-case Windows manual matrix is incomplete. No component may represent the
pre-release as fully real-device validated.

## Validation Profiles

The release tooling supports two explicit, mutually exclusive profiles.

| Profile | Tag | Evidence | Windows provenance | Intended publication |
| --- | --- | --- | --- | --- |
| `formal` | `v0.3.0` | `docs/validation/windows-v0.3.0.json`; all 130 cases pass | `realDeviceValidated: true` | stable release |
| `quick-prerelease` | `v0.3.0-rc.1` | `docs/validation/windows-v0.3.0-quick-prerelease.json`; strict x64 smoke record | `realDeviceValidated: false`, `validationProfile: "quick-prerelease"` | public pre-release |

The existing full-matrix validator remains the authority for `formal`. It does
not gain a skip, waiver, or partially-passed mode. The new quick evidence has
a separate exact schema and verifier; it records only independently observable
facts: Windows 11 AMD64/x64 identity, Codex file build, source SHA, UTC
completion time, setup embedded-payload verification, installed manager/runtime
health, and a default-redacted UIA probe. The record has fixed fields and
enumerated pass/fail values; it contains no raw UIA names, screenshots, task
content, user tokens, or free-form success claims.

The source commit `S` is frozen after the profile-support code and release
notes are committed. The sole allowed `S` to packaging commit `P` delta is the
profile's canonical evidence JSON. The smoke evidence binds to `S`; the
workflow binds provenance and all six assets to `P` and the exact Actions run.

## Build and Candidate Flow

The Windows setup builder, payload manifest builder, setup verifier, Windows
provenance finalizer, and aggregate candidate verifier receive an explicit
profile/tag contract. They reject an evidence path, validation status,
provenance status, or release tag belonging to the other profile. A quick
Windows candidate remains `publishableInstaller: true`, but it must carry the
unambiguous quick-profile fields and cannot be accepted by the formal verifier.

The macOS candidate remains a fresh v0.3.0 arm64 build. No macOS v0.2.3
application, DMG, provenance, workflow, tag, or release asset is modified.
Both finalizers bind the candidate to `v0.3.0-rc.1`, and the aggregate verifier
requires both platform records to name the same profile, tag, packaging SHA,
validated source SHA, repository, and Actions run.

The candidate workflow runs only after a canonical formal or quick evidence
file is committed on `v0.3.0`; ordinary source pushes cannot create an
un-evidenced candidate. Its existing pinned actions, read-only permissions,
exact-artifact staging, link/reparse rejection, and six-file aggregate
verification remain mandatory.

## Public Release and Boundaries

After the exact candidate run succeeds, its six-file bundle is downloaded by
exact run ID and independently verified. The Windows setup is then verified,
installed, launched, and uninstalled on this Windows 11 AMD64/x64 device using
the candidate bytes. The final publication is a new annotated `v0.3.0-rc.1`
tag and `gh release create --prerelease`; it never overwrites release assets
and never uses `--clobber`. The published assets are downloaded again and
verified against their recorded SHA-256 values.

The release notes must state all of the following:

- Windows support is Windows 11 AMD64/x64 only; Windows ARM64 is unsupported.
- The Windows setup is unsigned (`NotSigned`); users must verify the published
  SHA-256 and expect Windows SmartScreen's unknown-publisher warning.
- The 130-case Windows manual matrix is not complete. The release has passed
  automated gates and the limited x64 smoke record only.
- Unknown or unsupported UIA structures still hide the overlay; no coordinates
  are guessed.
- Single-monitor scope is validated; cross-monitor movement, cross-monitor
  DPI transitions, and negative-coordinate placement are not claimed.

No tag, Release, asset upload, workflow rerun, or public statement occurs if a
gate, candidate check, smoke check, asset checksum, or post-upload download
check fails.

## Testing

Tests must demonstrate that:

1. formal and quick schemas reject each other's evidence and tags;
2. quick evidence rejects missing, malformed, non-redacted, wrong-platform,
   wrong-source, or non-passing smoke values;
3. setup/payload/provenance/candidate verification preserves the formal path
   and accepts a quick candidate only with its exact profile markers;
4. the workflow triggers from canonical evidence only, passes the exact profile
   and tag to both platform finalizers, and cannot upload unverified assets;
5. release documentation exposes the quick-release boundaries and preserves the
   v0.2.3 freeze; and
6. all existing .NET, PowerShell, Python, Git Bash, workflow-contract, version,
   and v0.2.3 immutability gates remain green before `S` is frozen.
