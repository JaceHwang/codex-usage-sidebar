# Codex Usage Sidebar v0.3.0 Complete Release Chain Design

## Context

The Windows implementation is visible and operational on the real Windows 11 AMD64 development
device. The current functional baseline is commit
`4e67f34a55841498238916f4b1951917c1f0c92a`: it supports the observed Codex file build
`151.0.7922.76`, follows window movement and resizing, and places the compact overlay beside Open
Location in the middle tab title bar. The complete Windows test suite currently passes, but the
repository does not yet contain the canonical real-device evidence required by the release-candidate
workflow.

This design covers the remaining path from the current baseline to a public `v0.3.0` release. It
does not authorize publication until every gate below has passed.

## Goals

- Validate the final Windows source on a real Windows 11 AMD64 device using the complete release
  matrix defined by the repository schema.
- Produce an evidence-bound, per-user Windows x64 setup that users can install, repair, and
  uninstall without administrator privileges.
- Publish the Windows setup without Authenticode signing while giving users a verifiable download,
  checksum, provenance, self-check, and accurate SmartScreen guidance.
- Build a macOS arm64 v0.3.0 candidate from the same validated source and packaging commit.
- Publish both candidates through one auditable GitHub v0.3.0 release chain.
- Preserve every existing macOS v0.2.3 release asset and its digest.

## Non-goals

- Windows ARM64 support, builds, tests, packages, or release assets.
- Suppressing, bypassing, or disabling Microsoft Defender SmartScreen or other Windows security
  controls.
- Claiming that the unsigned Windows setup has an Authenticode signature.
- Expanding a known-build UIA fallback to unvalidated Codex builds.
- Redesigning the macOS interface or changing the approved macOS v0.2.3 visual behavior.
- Modifying, replacing, or re-uploading historical macOS v0.2.3 assets.
- Publishing screenshots, raw UIA names, task titles, account identifiers, or other private device
  evidence.

## Chosen Approach

Use an immutable, evidence-first release chain with two Git identities:

1. Finish all release documentation, tests, workflow gates, and packaging preparation.
2. Freeze the resulting source commit as `validatedSourceCommit`, referred to as `S`.
3. Install a nonpublishable x64 device-test payload built from `S` and complete the real-device
   matrix.
4. Add only `docs/validation/windows-v0.3.0.json` in a descendant commit, referred to as
   `packagingCommit` or `P`.
5. Build Windows x64 and macOS arm64 candidates from `S`, with provenance also recording `P` and the
   GitHub Actions artifact identity.
6. Re-download and verify candidates, create a draft release, re-download and verify the draft
   assets, then publish.

The current commit `4e67f34a55841498238916f4b1951917c1f0c92a` is a functional baseline, not a
predeclared `S`. Release instructions and any gate corrections must be completed before `S` is
frozen. This prevents documentation or workflow changes after validation from violating the
evidence-only packaging delta.

## Release State Model

The release advances through six ordered states:

1. **Prepared:** release documentation and automated gates are complete, and a clean source commit
   is ready to freeze.
2. **Source frozen:** `S` is immutable and its x64 device-test payload is installed on the real
   validation device.
3. **Device validated:** all 130 canonical Windows cases pass against `S`.
4. **Evidence committed:** `P` adds only the canonical validation JSON, and the packaging-delta gate
   proves no other path changed.
5. **Candidates verified:** both CI candidates and their finalized provenance pass independent
   download verification.
6. **Released:** draft assets pass a second download verification and the public release is checked
   without changing v0.2.3 assets.

A failed gate cannot be waived by advancing to the next state. A product, packaging, dependency,
workflow, or release-documentation change after `S` is frozen produces a new `S` and invalidates the
entire real-device matrix.

## Platform Scope and Compatibility

Windows support is Windows 11 build 22000 or newer on AMD64 hardware, represented as `x64` and
`win-x64` by the build toolchain. Every Windows platform, payload, setup, provenance, and filename
check must reject ARM64.

The observed official Codex file build is `151.0.7922.76`. Its validated title-bar topology may use
the narrowly approved window-relative fallback when exact UIA selection fails. Other Codex builds,
non-official hosts, invalid or non-finite window bounds, and missing or stale quota data must hide
the overlay. Geometry must never be guessed for an unknown build.

## Preparation Before Source Freeze

Before selecting `S`, update and test the public documentation and release surfaces:

- English and Simplified Chinese README platform status and Windows download entry.
- Windows installation, repair, upgrade, uninstall, and troubleshooting instructions.
- An explicit unsigned-setup and SmartScreen section in both supported documentation languages.
- `docs/releases/v0.3.0.md` with platform scope, known-build behavior, privacy, checksums, provenance,
  and support boundaries.
- Automated assertions that Windows is x64-only and historical v0.2.3 assets remain frozen.

The SmartScreen instructions must tell users to download only from the project GitHub v0.3.0
Release, verify SHA-256 first, expect an Unknown publisher warning, and continue with More info then
Run anyway only after the digest matches. They must tell users to delete a mismatched download and
must never ask users to disable Defender, SmartScreen, antivirus, or system policy.

Preparation ends only when the full local automated gate passes and the worktree is clean. The exact
HEAD at that point becomes `S`.

## Real-device Validation Environment

The canonical matrix runs on a Windows 11 AMD64 device as a normal signed-in desktop user. Before
recording any case:

- Confirm the branch is exactly `v0.3.0` and record the full lowercase SHA for `S`.
- Confirm the worktree is clean and the installed payload reports `sourceCommit=S`.
- Confirm the operating system is Windows 11, hardware and runtime are AMD64/x64, and the actual
  Windows build and four-component Codex file build are recorded.
- Use a disposable Codex task containing only non-sensitive placeholder content.
- Confirm valid quota data and a valid official Codex host window.
- Use the default-redacted UIA probe. Do not use `--include-text` for release evidence.

Temporary screenshots and probe reports may be used for local inspection, but they are not
committed. They must not include real task names, account details, filesystem paths, notifications,
or other applications.

## Canonical Windows Matrix

The repository schema defines 130 required cases: 108 visual, 9 geometry, 6 interaction, and 7
lifecycle cases. Every canonical case must have the exact shape accepted by
`scripts/verify-windows-v030-validation.py` and a result of `pass`.

### Visual matrix: 108 cases

The visual product is:

- Layout: `restored-collapsed`, `right-wide`, `left-right-expanded`.
- Theme: `light`, `dark`, `system`.
- Language: `zh-CN`, `zh-TW`, `en-US`.
- Display scale: 100, 125, 150, and 200 percent.

Execute these as 36 environment batches. For each theme, language, and scale combination, validate
the three layouts consecutively. A visual case passes only when:

- The compact overlay is attached to the middle tab title bar beside Open Location, not the top
  application title bar.
- The local Open Location placement is preferred when safe; the validated right-toolbar region is
  used only when the local region is obstructed or too narrow.
- The overlay is fully contained and does not overlap validated title or button obstacles.
- Simplified Chinese, Traditional Chinese, and English copy is complete and not clipped.
- The version capsule, digit/unit hierarchy, border, radius, spacing, and detail-card treatment stay
  aligned with the macOS v0.2.3 visual baseline.
- The progress bar keeps a full neutral track and clips a fixed full-width spectrum to the remaining
  fraction.
- Light, dark, and system themes remain legible and follow the Codex host appearance.

`system` is the third canonical theme. Windows high-contrast mode is an additional publication
blocker check, but it is not recorded as a fabricated extra canonical visual case.

### Geometry matrix: 9 cases

The required states are `restored-collapsed`, `left-expanded`, `right-expanded`, `right-wide`,
`left-right-expanded`, `bottom-expanded`, `narrow-window`, `maximized`, and `fullscreen`.
No additional geometry state is canonical.

The overlay must follow movement and resizing, recompute after DPI changes, switch safely between
local and right-toolbar placement, return to local placement when space returns, and hide if no
validated region is safe. The v0.3.0 release matrix is single-monitor: its evidence makes no claim
about cross-monitor movement, cross-monitor DPI transitions, or negative-coordinate placement.

### Interaction matrix: 6 cases

- `hover`: the detail card opens and remains stable while moving between indicator and detail.
- `pin`: a click pins the detail card and the documented second action closes it.
- `keyboard-focus`: the overlay does not steal typing focus.
- `no-activation`: displaying or interacting with the overlay does not activate or interrupt Codex.
- `resize-drag`: the overlay follows live resizing without remaining at stale coordinates.
- `unknown-structure-fail-hidden`: unvalidated, incomplete, ambiguous, or unsafe UIA input hides the
  overlay.

The exact-build fallback for `151.0.7922.76` does not relax the unknown-build fail-hidden rule.

### Lifecycle matrix: 7 cases

The required cases are `sleep-resume`, `codex-restart`, `codex-upgrade`, `authorization`, `install`,
`repair`, and `uninstall`. They verify recovery, single-instance behavior, per-user autostart,
authorization loss and restoration, no official Codex-file mutation, and cleanup of managed
processes and autostart entries.

The matrix first uses the nonpublishable device-test manager built from `S`, because the
publishable setup cannot exist until the matrix evidence has passed. The device-test manifest must
remain `status=device-test`, `realDeviceValidated=false`, and `publishableInstaller=false`.

For `codex-upgrade`, a new or changed UIA structure is expected to hide safely. Supporting a new
build requires a TDD source change, a new `S`, and a complete matrix restart.

## Evidence Format and Failure Rules

Generate the pending template with `scripts/new-windows-v030-validation-template.py`. The final
canonical file is exactly `docs/validation/windows-v0.3.0.json` and contains only schema version,
release version, `S`, x64 architecture, Windows build, Codex file build, UTC completion timestamp,
and the four case groups.

Evidence contains no free-form notes, screenshots, paths, UIA text, or personal identifiers. Before
commit, `scripts/verify-windows-v030-validation.py` must accept all 130 unique cases as passed.

Failures are handled as follows:

- An environment-operation mistake invalidates and repeats only the affected case when neither
  source nor tested product changed.
- A product defect stops the matrix. Apply a TDD fix, create a new `S`, and restart all 130 cases.
- A change to source, dependencies, packaging, workflows, or release documentation after freeze
  creates a new `S` and restarts all 130 cases.
- A Codex file-build change restarts the matrix with a new template and recorded build.

Commit the verified evidence as `P`. The diff from `S` to `P` must contain only
`docs/validation/windows-v0.3.0.json`.

## Windows x64 Release Candidate

The evidence-bound candidate consists of:

```text
codex-usage-sidebar-v0.3.0-windows-x64-setup.exe
WINDOWS-V030-SHA256SUMS.txt
WINDOWS-V030-PROVENANCE.final.json
```

The setup builder must run on the exact `v0.3.0` branch with a completely clean worktree, use the
canonical committed evidence, prove the evidence-only delta from `S` to `P`, and write outside the
repository. It builds only `win-x64`, pins the official Codex runtime URL and digest, and rejects
missing files, extra files, digest mismatches, links, reparse points, wrong architecture, or an
untrusted runtime source.

Release mode accepts only assembly-embedded payload files enumerated by the trusted manifest. It
does not accept an arbitrary command-line payload directory. The single-file setup must pass
`--verify-embedded`, install only for the current user, avoid administrator elevation, and never
modify the official Codex installation.

The setup is intentionally unsigned. Provenance records the actual Authenticode state and must not
claim a signature. Supply-chain integrity comes from the GitHub Release origin, SHA-256,
GitHub Actions artifact provenance, the trusted embedded manifest, and setup self-verification.

After CI produces the formal candidate, repeat the installer closure on the real Windows device:
fresh install, repair, upgrade/overwrite, uninstall, and reinstall. Verify autostart, exactly one
managed host, overlay visibility, preservation semantics, complete cleanup, and rollback behavior.
A failure is a product or packaging defect that requires a new `S` and a complete matrix restart.

## macOS arm64 Release Candidate

The macOS candidate consists of:

```text
codex-usage-sidebar-v0.3.0-macos-arm64.dmg
MACOS-V030-SHA256SUMS.txt
MACOS-V030-PROVENANCE.final.json
```

Build it on the pinned GitHub Actions arm64 runner and approved SDK. Run the Swift release tests,
v0.3.0 packaging gates, and v0.2.3 freeze tests. Verify bundle and plugin version, arm64 binary
architecture, existing codesign expectations, mountable DMG structure, checksum, and provenance.

The candidate records the same `S` and `P` as Windows. It preserves the macOS v0.2.3 UI baseline and
does not modify or republish any v0.2.3 asset. Record and compare historical v0.2.3 asset identities
and digests before candidate publication, before final release, and after final release.

## GitHub Actions and Provenance

Pushing `P` to `v0.3.0` triggers the Windows x64 and macOS arm64 candidate jobs. Both jobs verify the
canonical evidence before building. The Windows job runs .NET Release tests, formatting, payload,
setup, and embedded integration gates. The macOS job verifies its arm64 toolchain and SDK, runs
Swift and release-boundary tests, and mount-verifies the DMG.

Each job uploads its candidate, checksum, and initial provenance, then finalizes provenance with the
repository, branch, workflow path, run ID and URL, HEAD SHA `P`, validated source SHA `S`, artifact
ID, artifact name, artifact digest, and release tag. Artifact upload alone is not publication.

If a runner fails without any source or environment-definition change, the same `P` may be rerun.
Any change to code, scripts, dependencies, workflows, documentation, or packaging creates a new
`S` and restarts validation.

GitHub CLI is the release-control client on the Windows AMD64 validation device. Install the
official `GitHub.cli` package from the `winget` community source and authorize it through the GitHub
browser flow without exposing a token. Use `gh run list`, `gh run watch`, and `gh run download` to
bind candidate inspection and download to an exact run ID. Use `gh release create --draft` to create
the six-asset draft, `gh release download` for independent draft/public re-downloads, and
`gh release edit --draft=false` only after the final go/no-go gate. The browser remains an optional
human-readable cross-check, not the source of artifact identity.

Release commands must always specify `--repo JaceHwang/codex-usage-sidebar`, the exact tag/run ID,
and explicit asset paths. Never use `gh release upload --clobber`; an asset mismatch invalidates the
draft instead of authorizing an in-place replacement. GitHub CLI is a developer/release dependency,
not a runtime requirement for plugin users.

## Candidate Download Verification

Download every candidate and finalized provenance file to an isolated local directory. Verify:

- Exact filenames, Windows x64 architecture, and macOS arm64 architecture.
- Every file digest against its checksum document.
- Repository, branch, workflow, run, artifact ID, and artifact digest in finalized provenance.
- Identical `S` and `P` across platforms.
- Windows embedded-payload self-verification and truthful unsigned Authenticode state.
- macOS DMG mounting, contents, version, architecture, and codesign expectations.
- Absence of probes, screenshots, task content, account data, and other temporary evidence.

Only downloaded CI artifacts that pass these checks may enter the GitHub Release. Do not rebuild a
local substitute.

## Draft and Public Release

Create a draft GitHub Release tagged `v0.3.0` only after both CI jobs and local candidate download
verification pass. Attach at least the Windows setup, Windows checksum, finalized Windows
provenance, macOS DMG, macOS checksum, and finalized macOS provenance.

The release notes state the supported architectures, Windows unsigned/SmartScreen behavior,
SHA-256 verification, install/repair/uninstall path, known Codex build behavior, unknown-UIA
fail-hidden policy, upgrade troubleshooting, and redacted-probe privacy policy.

Re-download all six assets from the draft and verify them again. Confirm the `v0.3.0` tag targets
`P`, the repository has no pending release changes, and historical v0.2.3 asset IDs and digests are
unchanged. Only then publish the release.

After publication, verify public downloads, digests, release links, Windows setup self-check, and
the unchanged v0.2.3 assets. Record the tag, `S`, `P`, workflow run URLs, artifact identities, and
all release-asset SHA-256 values in the release handoff.

## Rollback and Incident Policy

- Never silently overwrite a published asset or alter its historical checksum.
- A matrix failure returns to source development and a new `S`.
- A formal setup install failure returns to source development and a new `S`; it cannot be fixed by
  replacing only the binary.
- A draft verification failure invalidates the affected candidates and returns to the earliest
  failed gate.
- A severe post-release issue is documented and fixed in a new version such as `v0.3.1`; the
  published v0.3.0 assets remain immutable.
- A later Codex UIA change keeps the overlay hidden until a default-redacted report is inspected,
  exact-build support is added with TDD, and a new release passes its gates.

## Completion Criteria

The release chain is complete only when:

- The final source `S` passes all automated gates and all 130 Windows real-device cases.
- `P` differs from `S` only by the canonical evidence JSON.
- The Windows formal setup passes its separate real-device installer closure.
- Both platform candidates share `S` and `P` and pass CI plus independent download verification.
- The draft release passes a second independent asset verification.
- The public v0.3.0 assets, documentation, and checksums are reachable and correct.
- Windows provenance is truthful about the unsigned setup and documentation explains SmartScreen
  without weakening Windows security.
- Windows ARM64 remains rejected and all macOS v0.2.3 assets remain unchanged.
