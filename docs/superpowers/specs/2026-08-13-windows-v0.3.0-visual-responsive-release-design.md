# Codex Usage Sidebar v0.3.0 Visual, Responsive Placement, and Release Design

Date: 2026-08-13

## Scope and source of truth

This milestone corrects the five Windows issues shown in the two user-provided screenshots and then
promotes the repository to a new v0.3.0 release line for Windows x64 and macOS arm64. The approved
macOS v0.2.3 rendering remains the visual and interaction source of truth. Existing v0.2.3 GitHub
assets are immutable; v0.3.0 uses new filenames, provenance, checksums, and a new release.

The Windows implementation remains an external no-activate WPF overlay. It does not inject into or
modify the Codex application. Windows ARM64 remains outside this release.

## Visual corrections

### Countdown typography

The final parenthesized relative interval in each detail value is segmented using the same roles as
the macOS implementation: plain text, punctuation, digits, units, and suffix. For `（6d19h）`, `6`
and `19` use 14-logical-pixel semibold type and the live quota accent. Parentheses, `d`, and `h` use
10-logical-pixel type and the secondary text color. Absolute date text remains 12 logical pixels.
The parser also supports `h`, `m`, `<1m`, past-time suffixes, ASCII parentheses, and full-width
Chinese parentheses without styling unrelated numbers.

### Version badge

The detail header keeps the macOS order: localized title, version capsule, flexible space, and live
percentage. The capsule has an explicit 14-logical-pixel height, 8-logical-pixel medium text,
0.75-logical-pixel blue outline, five logical pixels of horizontal inset, and no vertical padding.
Both the capsule and its text are vertically centered instead of stretching to the header row.
During device testing it displays the current beta version; the promotion commit changes the shared
version source so the released badge reads `v0.3.0`.

### Compact control height

The compact control remains 164 logical pixels wide, but no longer uses a fixed 46-logical-pixel
height. Its physical Y coordinate and height come from the exact UIA bounds of the validated Open
Location button. At 200% scaling the currently measured 56 physical pixels therefore render as 28
logical pixels. The hover surface, hit-test surface, window frame, and collision frame all use that
same measured height. Width, typography, eight-logical-pixel trailing gap, no-activate behavior, and
click/hover semantics remain unchanged.

### Progress spectrum

The progress control always paints a full-width neutral track first, making the used portion
visible. Its fill uses one fixed full-width spectrum with the same stop positions as macOS:
critical red at 0%, red at 10%, orange at 49%, and green at 100%. A clip equal to the live remaining
percentage reveals the left portion of that full spectrum. The gradient coordinate space never
shrinks with the remaining percentage, so a 41% fill ends at the actual 41% spectrum color rather
than compressing green into the shortened fill.

## Responsive placement

### Validated UIA geometry

For the supported Codex build, the selector resolves all of the following from UIA physical screen
coordinates:

- the content toolbar and its direct content group;
- the exact Open Location button frame;
- the task-title cluster that precedes Open Location;
- the structural right-toolbar group above the right pane; and
- interactive buttons in the titlebar band, including right-pane close/collapse controls.

Two default-redacted fixtures cover the wide local-anchor state and the narrow fallback state. The
selector remains build-gated. Missing, duplicated, structurally changed, non-finite, off-host, or
ambiguous nodes invalidate the snapshot and hide the overlay. Runtime selection never invents a
screen coordinate.

### Local placement

The preferred frame ends exactly eight logical pixels before Open Location and uses the anchor's
measured Y and height. The complete 164-logical-pixel frame must fit between the task-title cluster
and Open Location without intersecting any measured toolbar obstacle. This makes the wide layout
match the current desired placement while preventing the screenshot-2 title overlap.

### Right-side fallback

If the complete local frame does not fit, the resolver uses the build-validated structural
right-toolbar group. It places the same control at the group's right side, immediately before the
measured right-side button cluster, with the same eight-logical-pixel gap and anchor-aligned height.
The frame must remain fully inside the validated right-toolbar group and clear every measured
interactive obstacle. If the right group or its safety boundary cannot be proven, the overlay hides
instead of falling back to the outer Windows caption.

Placement is recomputed on the existing 100-millisecond cadence. The current 750-millisecond
retention window may bridge transient UIA refreshes only while host identity, DPI, geometry, and the
retained frame remain safe. Resizing back to a wide layout returns the control to Open Location.

## Component boundaries

- `CodexUsageSidebar.Core` owns countdown segmentation, progress spectrum stops, and two-zone
  placement calculations in platform-neutral types.
- `CodexUsageSidebar.Windows` owns build-gated UIA extraction, WPF inline typography, the progress
  renderer, physical positioning, and no-activate windows.
- Version strings come from one build property/assembly source rather than separate WPF literals.
- Sanitized UIA fixture construction and verification remain in repository scripts and tests.

## Testing and real-device evidence

TDD must demonstrate:

- exact countdown roles for future, past, minute-only, malformed, ASCII, and full-width forms;
- fixed gradient stop positions and clip fractions at 0, 10, 41, 49, and 100%;
- explicit badge metrics and measured compact-control height;
- wide local placement, title collision, narrow right fallback, return-to-wide behavior, DPI scaling,
  obstacle rejection, and fail-hidden unknown structures;
- WPF no-activate flags and existing hover/pin behavior; and
- version promotion and artifact-name consistency.

Real-device evidence uses only a disposable Codex task and default-redacted reports. At minimum it
captures wide and narrow content layouts at 200%, verifies the requested fallback transition while
dragging the pane, confirms hover-card typography and progress rendering, checks focus remains in
Codex, and restores the original window geometry. Publication still requires the full Windows 11
x64 matrix already defined by the handoff documents: light/dark/high contrast, three languages,
100/125/150/200% DPI, multiple monitors, pane/fullscreen states, hover/pin/focus, sleep/resume,
Codex restart/update, authorization, install, repair, and uninstall.

## v0.3.0 promotion and release

After the visual and real-device gates pass, create the exact user-requested branch `v0.3.0` from
the verified development commit. A single promotion changes the unified plugin version, Windows
assembly/payload/installer version, macOS bundle/installer version, documentation, release notes,
workflow filters, artifact names, and cache-buster to v0.3.0. macOS behavior is not redesigned; it
is rebuilt from the verified source as a new v0.3.0 arm64 asset.

The v0.3.0 release candidate contains:

```text
codex-usage-sidebar-v0.3.0.zip
codex-usage-sidebar-v0.3.0-windows-x64-setup.exe
codex-usage-sidebar-v0.3.0-macos-arm64.dmg
SHA256SUMS.txt
WINDOWS-PROVENANCE.json
MACOS-INSTALLER-PROVENANCE.json
```

The Windows setup remains per-user, non-elevated, x64-only, provenance-bound, and signed-state
explicit. The macOS artifact is built and verified on the pinned macOS CI runner. Every published
file must match the tested source commit and recorded digest. The branch may be pushed for CI and
review before release publication, but setup/DMG assets are uploaded only after their platform
gates pass. No command overwrites, replaces, or re-uploads a v0.2.3 asset.
