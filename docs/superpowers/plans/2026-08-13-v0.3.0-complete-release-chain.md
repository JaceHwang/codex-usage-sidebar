# Codex Usage Sidebar v0.3.0 Complete Release Chain Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish the remaining documentation and release tooling, validate the final Windows 11 x64 source on the real device, produce provenance-bound Windows x64 and macOS arm64 candidates, and publish GitHub release v0.3.0 without changing macOS v0.2.3 assets.

**Architecture:** All mutable release preparation finishes before freezing an immutable validated source commit `S`. A nonpublishable Windows x64 device-test payload built from `S` receives the complete 131-case real-device matrix; a descendant packaging commit `P` may add only `docs/validation/windows-v0.3.0.json`. Existing builders create both platform candidates from `S` while provenance records `P`; new read-only helpers make matrix recording, candidate-set verification, and historical v0.2.3 asset comparison deterministic.

**Tech Stack:** .NET 8/WPF, PowerShell 5.1+, Python 3, Bash via `D:\app\Git\bin\bash.exe`, GitHub CLI 2.97.0 or newer, Swift 6/AppKit on GitHub Actions macOS arm64, GitHub Actions, GitHub REST API, SHA-256, Git provenance.

## Global Constraints

- Windows support is Windows 11 build 22000 or newer on AMD64 hardware, named `x64`/`win-x64`; Windows ARM64 must be rejected everywhere.
- The Windows setup is intentionally Authenticode-unsigned. Record `NotSigned` truthfully and explain SmartScreen; never bypass or disable Windows security controls.
- Default UIA reports remain redacted. Never use `--include-text` for release evidence or commit raw probes/screenshots.
- Exact build `151.0.7922.76` may use only its approved relative fallback. Unknown, ambiguous, unsafe, or changed UIA structures hide the overlay.
- macOS v0.2.3 assets, digests, source boundary, and publishing workflow are immutable and must not be modified or re-uploaded.
- Finish Tasks 1-5 before freezing `S`. Any code, dependency, workflow, packaging, or release-documentation change after Task 6 invalidates `S` and restarts Tasks 6-9.
- The real-device matrix cannot be inferred or bulk-marked. Each case is marked pass only immediately after the named manual observation succeeds.
- Do not publish a setup, create a release tag, or create a GitHub Release until the preceding gate explicitly permits it.
- Install official `GitHub.cli` from the `winget` community source on Windows x64 and authenticate with `gh auth login --hostname github.com --git-protocol https --web --skip-ssh-key`. Never expose a token.
- Every `gh` run/release command must specify `--repo JaceHwang/codex-usage-sidebar` and an exact run ID, tag, commit, or asset path. Never use `gh release upload --clobber`.

## File Responsibility Map

- `README.md`, `README.zh-CN.md`: public platform status, download path, unsigned Windows warning, and quick install instructions.
- `docs/INSTALL.md`: platform-separated install, repair, upgrade, uninstall, checksum, and SmartScreen operations.
- `docs/TROUBLESHOOTING.md`: Windows visibility, unknown-build fail-hidden, SmartScreen, and sanitized-probe diagnosis.
- `docs/releases/v0.3.0.md`: final release notes used as the GitHub release body.
- `tests/test-v030-release-docs.py`: executable public-documentation contract; it must never depend on unpublished evidence.
- `scripts/record-windows-v030-validation.py`: atomic single-case evidence recorder; it never decides whether a case passed.
- `tests/test-windows-v030-validation-recorder.py`: exact-key, duplicate, pending, completion, and schema-preservation tests for the recorder.
- `scripts/verify-v030-candidate-set.py`: read-only verifier for the six downloaded release assets and shared `S`/`P` provenance identity.
- `tests/test-v030-candidate-set.py`: positive and tamper fixtures for the candidate-set verifier.
- `scripts/snapshot-github-release-assets.py`: read-only GitHub REST snapshot/compare helper for immutable v0.2.3 assets.
- `tests/test-github-release-asset-snapshot.py`: offline fixtures for sorting, identity, digest, URL, and mismatch handling.
- `.github/workflows/v030-release-candidates.yml`: existing two-platform build plus a final verified six-file release-bundle artifact; it never publishes a GitHub Release.
- `tests/test-v030-release-candidate-workflow.sh`: static workflow gate for candidate and bundle behavior.
- `docs/validation/windows-v0.3.0.json`: the only file allowed in packaging commit `P` after real-device validation.

## Restart Matrix

Use this table whenever a gate fails:

| Failure | Resume point |
| --- | --- |
| Manual environment mistake with unchanged `S` | Repeat only the affected unrecorded case in Task 7 |
| Product/UI/installer defect | TDD fix, then restart at Task 6 with a new `S` |
| Tracked code, dependency, workflow, packaging, or release-doc change after `S` | Restart at Task 6 with a new `S` |
| Codex file build changes during validation | New template and restart Tasks 6-8 |
| Transient GitHub runner/service failure with unchanged `P` | Rerun the exact job in Task 8 |
| Candidate or formal setup verification failure | New `S`; restart Tasks 6-9 |
| Draft asset mismatch | Invalidate draft assets and return to Task 8 or 9 based on source of mismatch |
| Severe issue after publication | Keep v0.3.0 immutable and prepare a new version such as v0.3.1 |
